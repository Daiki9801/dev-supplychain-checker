# Limitations

This scanner is designed for safe initial triage.

## How To Interpret A Result

| Report state | What it establishes | What it does not establish |
|---|---|---|
| `complete` | The planned checks completed inside the selected bounded scope. | That the host, repository, disk, dependencies, or binaries are clean. |
| `partial-non-critical` | Critical candidate coverage completed, but at least one declared non-critical operation or bounded analysis did not. | A completed negative result for the skipped operation or content. |
| `incomplete-critical` | A material planned area could not be enumerated, read, or parsed. | A reliable negative result. |
| `error` | Scanner or report execution failed. | Any negative security conclusion. |

Severity is independent of completion. `DANGER` is a high-priority review candidate, not proof of infection. No `DANGER` finding is not proof of safety.

## Detailed Boundaries

- It does not prove that a host or repository is clean.
- It does not perform network lookups or online IOC refresh.
- It does not verify whether package names exist in npm, PyPI, OpenVSX, or other registries.
- It does not judge package popularity, maintainer trust, provenance authenticity, or slopsquatting/package-hallucination risk unless an exact offline IOC is provided.
- Large supply-chain campaigns require manual IOC updates; incomplete public package lists should not be treated as complete coverage.
- It does not remediate, delete, quarantine, uninstall, rotate tokens, or modify registry/settings.
- It does not execute target project code, package-manager commands, hooks, workflows, or build scripts.
- It does not run `npm root -g`, `npm cache ls`, `git clone`, `git archive`, or GitHub download/API retrieval. GitHub repositories must be supplied as local folders by the user.
- `-Checks Recommended` excludes npm global/cache and host Node.js location discovery. `NpmGlobal` and `NpmCache` are static, bounded, opt-in check categories; known-path Node.js host discovery is limited to `MajorRecommended`, `AllSafe`, or explicit broader host modes.
- YAML and TOML use bounded line-oriented parsers. npm `package-lock.json`/`npm-shrinkwrap.json` and Python `Pipfile.lock` are structurally parsed as JSON; pnpm and Yarn lockfiles use bounded format-specific parsers. Malformed critical lockfiles and unsupported binary `bun.lockb` are reported as incomplete candidate coverage rather than inferred by proximity text.
- Dependency directories are targeted by default; absence of findings inside `node_modules`, `.venv`, or `vendor` is not a complete dependency audit.
- Deep-only dependency/generated code is not assumed to be an active execution path. Generic secret-send, developer-tool write, single invisible-Unicode execution, and local WASM decode/process compounds in files that were not selected as package lifecycle/runtime entrypoints are capped at `WARN`; generic fetch-execute helpers are `CAUTION`. Exact IOC/campaign evidence and first-party or selected entrypoint behavior retain their normal higher-priority classification.
- `.github/workflows` files nested under dependency or generated-artifact directories are not active workflows in the consuming repository and are excluded from GitHub Actions-specific evaluation. Other applicable static code and exact-IOC checks still run.
- Embedded executable fixtures remain in normal behavior and IOC analysis. Test-like function names, helper names, here-string structure, and fixture-/pattern-like variable or array names are not treated as proof that attacker-controlled content is passive; trusted distribution samples use separate bounded manifest/path controls. For the generic PowerShell fetch-execute heuristic only, original-source matches whose source and sink anchors both fall inside proven static `Pattern` literals may be classified `PassiveRegex`. The proof is limited to a lexical function scope, direct `-match`/`-notmatch` consumers, and reachable local helpers that cannot capture the value through dynamic scope. Active matches take priority and keep their original line. Parse failure, reflection, self-source reads, wrappers, property/index transfer, execution-oriented use, or unknown flow remains a fail-safe finding. Match enumeration is bounded to 64 matches per signature; reaching the sentinel match produces an `Ambiguous` fail-safe finding instead of suppressing the remainder. This is conservative static flow analysis, not a proof that arbitrary PowerShell is safe.
- Targeted npm runtime-entrypoint selection ignores TypeScript declaration files (`.d.ts`, `.d.mts`, `.d.cts`) and source maps because they are not executable runtime entrypoints; their package metadata and resolved JavaScript entrypoints remain in scope.
- Variation Selector analysis and each in-memory static payload decode buffer are limited to 8,192 selectors/bytes. Over-limit input receives a bounded tail search for consecutive clusters, is reported as incomplete candidate coverage, and does not block remaining files. A marker located only beyond the decode prefix is not separately classified as a decoded-payload marker.
- Child-project discovery is bounded to depth 4 (8 in Deep), 500 project roots, and 20,000 directories. Dependency targeting uses at most `min(10,000, floor(MaxFiles * 0.5))` files, divided across discovered projects with a 2,000-file per-project ceiling. This keeps broad parent scans responsive while preserving at least half of the run budget for normal source and configuration; a narrower project or explicit Deep scan is required for broader dependency content.
- `filesEnumerated` counts observations and may include duplicates; `uniqueFilesQueued` is the run-wide deduplicated count governed by `MaxFiles`.
- BOM-less UTF-16 detection uses at most the first 64 KiB as its encoding probe, then decodes the complete bounded file when UTF-16 is indicated. Common binary extensions skip ordinary text parsing after exact hash and relevant IDE/native artifact checks; this reduces false text scanning but does not perform general binary reverse engineering.
- Every full-text regular-expression operation has an explicit two-second .NET timeout; the process-wide default is defense in depth for short metadata and path checks. This is a per-operation limit, not an overall scan timeout. `REGEX_SCAN_TIMEOUT` means only that operation was skipped for the named file; other checks and files continue. The run cannot be `complete`: it is `partial-non-critical` for a non-critical candidate and `incomplete-critical` when the timed-out file is a critical candidate such as a lockfile or active configuration. Generated, minified, or adversarial text can trigger this limit. Narrow the target or review the file manually instead of treating a larger timeout as evidence that the file is safe.
- Deep is explicit opt-in. It enters dependency, build, and cache directories but does not add npm global/cache, UserProfile, MajorLocations, or EndpointTelemetry. VCS, reparse points, auth-file contents, verified fixture protection, and the running checker's report exclusion remain enforced.
- Endpoint telemetry is opt-in, bounded, and best-effort.
- User profile scanning is opt-in. Known credential files are inventory-only; other in-scope configuration, session, and cache text may be read for static matching, while paths and secret-like evidence are centrally redacted in reports.
- MajorLocations mode scans common developer and AI-tool locations only, including bounded Desktop/IDE-default and OneDrive project subfolders when the OneDrive environment root is a safe child of `USERPROFILE`. Codex coverage is limited to selected active configs, agents, rules, skills, installed plugin tooling, and extension roots; `.codex\sessions`, runtime cache, and history data are excluded. It does not recurse through the whole Desktop, Documents, user profile, or disk.
- Launcher `full` adds MajorLocations, UserProfile, static npm global/cache, known-path/PATH Node.js metadata, and EndpointTelemetry to the explicit target. It remains bounded, is not full-disk, and does not imply Deep dependency/build/cache recursion.
- Parent-directory and MajorLocations scans skip only synthetic fixture files that match the currently running checker manifest by safe relative path and hash or presence rule. Unrelated project `tests/samples` directories, unknown files, modified files, and fake scanner artifacts are still scanned.
- Script-only or incomplete checker copies can still run for compatibility, but reports include `scanner.distributionStatus` and incomplete copies disable external scanner-artifact sample trust.
- External checker artifact manifests are not trusted. Only the currently running distribution's manifest can identify known synthetic fixture hashes.
- Emoji presentation selectors such as `U+FE0F` are suppressed in documentation and dependency metadata unless paired with executable-code context.
- `.codex` content is classified by context. Active configs and executable tooling can still produce `DANGER`, while reference text, session logs, cache data, and plugin metadata without command fields are aggregated as lower-priority context. Session and runtime-cache aggregation applies when those files are explicitly in scope, such as UserProfile or full mode; MajorLocations excludes them.
- Active AI instruction files such as `AGENTS.md`, `CLAUDE.md`, Cursor rules, and GitHub Copilot instructions are operational input. Fetch-execute or credential-send shaped guidance is reported as `WARN`; text alone is not treated as proof that an agent executed it.
- Capability findings for AI tools indicate that a local skill or plugin can access a network/API/install surface; they are not proof of infection by themselves.
- `active-exfil` and `known-ioc` findings are higher priority than capability-only findings.
- `DANGER` is reserved for known-bad IOC matches or strong execution/exfiltration context. `WARN` is a higher-priority review candidate. `CAUTION` is a lower-signal presence, capability, or posture finding without a strong malicious compound. None of these labels alone proves infection.
- GlassWorm-style C2 markers such as blockchain, DHT, calendar, paste, gist, or raw-host patterns are triage signals. They become high priority only when paired with execution, decoding, invisible Unicode, or credential-access behavior in executable code or active execution configuration.
- GlassWorm decoder signatures require locally coupled selector-range checks and byte-offset mappings. A decoder without an observed Variation Selector cluster is `WARN` at most; unrelated references spread across a bundled file are not a decoder compound.
- GlassWorm-style decoder examples without an observed selector in `.codex` reference text, plus decoder-shaped text in session logs or cache data, are aggregated as low-priority context even when they describe execution or exfiltration patterns. Actual hidden selectors in reference text remain subject to the normal bounded Unicode analysis.
- AI skill reference text can contain risky examples. Executable-looking documentation examples are aggregated as `CAUTION`; active execution configuration is evaluated separately at higher priority.
- `priorityFindings` intentionally excludes reference/session/cache findings and avoids being filled by capability-only findings so executable risks are easier to review first. Explicit project/container Node.js `Critical`/`High` matches remain eligible, with a three-entry Node.js cap.
- `priorityFindings` also excludes scanner self-reference findings and manifest-verified scanner artifact samples. Untrusted scanner artifact sample files remain eligible for priority review.
- npm cache content blobs are skipped by default and counted in `scanStats`; manifests and lockfiles remain in scope. The 500-file metadata limit and partial status are disclosed under `coverage.summary`.
- npm cache metadata is weak evidence by itself. Cache-only matches are reported as `WARN` or `INFO`, not proof of install or execution.
- Broad incident family names such as TanStack, Mistral, and Red Hat npm package families are watchlist context only unless an exact affected version or strong behavior chain is present.
- Exact offline IOC matches, lifecycle/import-time secret harvesting plus external send, and external download plus execution remain high-priority findings.
- General semantic-version range inclusion is not evaluated. An exact installed, lockfile, or manifest version can be `DANGER`; a range or fallback text that mentions a bad version is capped at `WARN` until the resolved version is confirmed.
- The Keyv ChainDrop campaign snapshot is static and time-bounded. Its 443 package names and 2,235 exact pairs reflect the supplied incident artifacts reviewed on 2026-08-12; the checker does not independently refresh or network-reverify them. Missing, stale, malformed, truncated, duplicate, or canonical-hash-mismatched campaign data is disclosed in the report.
- `scanComplete=true` means traversal, directory access, and critical candidate processing all completed within the configured bounds. It does not mean every dependency file on disk was recursively inspected, and it does not prove absence of compromise. `completionStatus` distinguishes `partial-non-critical` from `incomplete-critical` and `error`; `coverage.summary` supplies the counts, bounded/sampled labels, and next action. `traversalComplete=false` is classified as `partial-non-critical` when every recorded gap is explicitly non-critical; run-wide `MaxFiles` exhaustion remains critical because the unenumerated remainder is unknown. `SCAN_COMPLETED` is emitted only for `completionStatus=complete`; a non-critical partial result receives an informational coverage finding and is still not proof that the host is clean.
- `workflow_dispatch` alone is a `CAUTION` posture item. It becomes `WARN` when the same workflow also exposes secrets, write permissions, or manual input consumed by a command step; stronger existing execution/exfiltration compounds still take precedence.
- A directory-level `PATH_TOO_LONG` finding can name the containing directory because the runtime does not always expose the exact child entry that triggered `PathTooLongException`.
- File-hash IOC detection applies only when the candidate file is reached by normal or targeted enumeration. The scanner does not recursively hash every file under dependency directories.
- Extension publisher/name/version metadata does not reliably identify the source registry. Cross-registry identity collisions require file hashes or behavior evidence.
- Remote WebAssembly loading and native/WASM artifact presence are `CAUTION` capability findings by themselves. A local decode/process compound in unselected dependency/generated code is `WARN`; exact IOC, known C2, secret exfiltration, or equivalent strong active context can still produce `DANGER`.
- GitHub Action refs cannot be resolved online. Known compromised commits are exact IOC matches, while historically affected or mutable tags remain review candidates.
- JetBrains inspection is static and bounded. It reads `META-INF/plugin.xml`, selected script entries, native-artifact names, and configured file hashes without extracting archives or executing code.
- JetBrains archives are limited to 200 MB and 5,000 entries; plugin XML to 1 MB; nested JARs to 20 entries, 25 MB each, and 50 MB total; scripts to 20 entries, 512 KB each, and 5 MB total. Malformed, encrypted, unsafe-path, or over-limit archives are reported as aggregated limitations.
- JetBrains `.class` files are not decompiled or searched as arbitrary bytecode strings. Marketplace origin, signatures, and online publisher status cannot be confirmed offline. Program Files and Toolbox bundled plugins require explicit `-Path`.
- A JetBrains native artifact alone is inventory/capability context, not `DANGER`. No production JetBrains IOC is shipped unless an exact ID/version or hash is independently verified.
- Node.js runtime coverage is deliberately bounded: official Critical releases from 2020 onward and the manually maintained recent-High window in `known-node-runtimes.json`. It is not a complete Node.js CVE audit and does not automatically classify EOL releases.
- Node.js version comparison accepts exact `major.minor.patch` values with optional prerelease/build metadata. General semver ranges, aliases, variables, Docker ARG values, registry resolution, and package-manager resolution are not evaluated.
- `engines.node` is a compatibility constraint, not proof of the installed runtime, so it is capped at `INFO`. Explicit project pins and accepted Windows file-version metadata are `WARN` when they match an affected range; version evidence alone is never `DANGER`.
- Windows file-version metadata does not prove binary authenticity or signature status. Broader host scopes inspect `node.exe` in bounded known locations and the top level of existing local process-PATH directories, but do not query the registry, use Authenticode network validation, or execute `node.exe`. UNC PATH roots and reparse-point roots are rejected.
- `nodeRuntimeAssessment.inventory` is limited to 100 deduplicated exact-version observations and uses redacted paths. `notAffected` means that the version did not match the shipped bounded offline advisory set; it does not establish full CVE coverage, EOL support, binary authenticity, or publisher provenance.
- Shai-Hulud style filenames such as `setup_bun.js`, `bun_environment.js`, `actionsSecrets.json`, and `truffleSecrets.json` are treated as context markers. They become high priority when paired with executable context, credential access, or artifact/exfiltration behavior.
- GitHub Actions workflows that combine discussion/comment body input, self-hosted runners, and execution context are high-priority because they can turn repository discussions into a runner execution surface.
- GitHub Actions workflows that serialize broad secrets into uploaded artifacts are high-priority credential exposure candidates.
- MajorLocations mode intentionally avoids broad `%USERPROFILE%\.config` recursion; use explicit UserProfile mode for broader profile config scanning.
- MajorLocations still checks targeted `.config` subfolders for Claude, Continue, Gemini, and OpenCode. UserProfile adds the broader `.config` tree plus common editor `settings.json`/`mcp.json`, custom `CODEX_HOME`/`CLAUDE_CONFIG_DIR`, and common extension roots. Environment-defined automatic roots must be absolute non-reparse children of `USERPROFILE`; rejected external roots require an explicit `-Path` scan.
- `iocData.releaseReady=false` is a publication-readiness signal, not a scan-abort condition. Historical exact IOCs stay active when a dataset becomes stale; missing or invalid files fall back only where an embedded baseline exists.
- Secret inventory reports file presence only and never prints secret values.
- Launcher custom menu item `8` accepts project-local checks only. Host-scoped npm checks and the `MajorRecommended`/`AllSafe` macros require their dedicated confirmed modes instead.
- The `tests/samples` directory contains synthetic fixtures that intentionally trigger findings; those findings do not indicate that the scanner project is infected.
